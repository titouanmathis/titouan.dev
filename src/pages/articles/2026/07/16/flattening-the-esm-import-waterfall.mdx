# Flattening the ESM import waterfall when you go buildless

<MetaInfo class="block">16/07/2026 in #esm #no-build #performance</MetaInfo>

I have been shipping a few buildless front-ends lately, with no bundler and no dev server, only native ES modules and a couple of imports from [esm.sh](https://esm.sh). It's a nice way to work: there is no configuration and the feedback is instant. The first time I opened the network panel on one of these pages, I found a long chain of requests where each one waits for the previous one to finish.

This is called the [module graph discovery waterfall](https://blacksheepcode.com/posts/loading_optimisations_part_4), and it comes with skipping the build step. In this article, I am sharing what it looks like on a real page and the techniques I use to avoid it.

<TableOfContent open />

## What the waterfall is

When the browser loads an ES module, it doesn't know that module's dependencies until it has downloaded and parsed it. Only then does it discover the next `import`, request it, parse it, discover the next one, and so on. A module doesn't execute until its entire static import graph has loaded, and a child can't start loading before its parent has finished.

On a bundled app this isn't an issue: the bundler already walked the graph and flattened it into a handful of files. When you go buildless against a CDN, every sub-module becomes its own HTTP request, so the depth of your dependency tree translates into round trips.

## A real capture

Here is one of our own pages: [ui.studiometa.dev](https://ui.studiometa.dev), which loads `@studiometa/js-toolkit` and a `modern-monaco` editor straight from esm.sh. That handful of `import` statements fans out into 176 requests to esm.sh over roughly 1.45 seconds. A single import, `@studiometa/js-toolkit@3.6.0?bundle=false`, accounts for 148 of them, one file per decorator, helper and util.

![Waterfall of 176 esm.sh requests, colored by package](/2026/07/16/esm-waterfall.svg)

Each bar is one request, sorted by start time, and the color is the package it belongs to. You can see that requests don't start together: each cluster only begins once the previous one has arrived and been parsed.

The same thing shows up as the number of requests known to the browser over time. It doesn't grow smoothly, it climbs in about twelve steps, and each step is one round trip worth of newly discovered modules:

![Cumulative discovered requests over time, climbing in discrete steps](/2026/07/16/esm-discovery-waves.svg)

## Multiplexing is not enough

A common assumption is that HTTP/2 or HTTP/3 multiplexes requests, so many small files are fine. Looking at the timings on this capture shows it isn't. All 176 requests went over HTTP/3, on a single connection, with zero queueing, so the transport was never the bottleneck.

The staircase is still there. Multiplexing removes the connection overhead, but it can't remove the discovery latency: the browser can only parallelize requests it already knows about, and it doesn't know about a deep module until its parent has arrived. The flat steps in the second chart are the browser waiting to discover what to fetch next. The bottleneck is latency, not throughput.

So the goal isn't to have fewer connections, but to flatten the graph, by making the browser aware of deep modules earlier or by collapsing the depth entirely.

## Flattening the waterfall

### Check your esm.sh bundling flags

The first thing to check is how you are bundling. `?bundle=false` tells esm.sh to serve every sub-module separately, which is what produced the 148-file fan-out above. The default already bundles sub-modules, and `?bundle` goes further and rolls the dependencies into a single response.

```js
// Don't: one import explodes into a deep tree of separate requests
import { Base } from 'https://esm.sh/@studiometa/js-toolkit@3.6.0?bundle=false';

// Do: let the CDN bundle the graph server-side, one response, no waterfall
import { Base } from 'https://esm.sh/@studiometa/js-toolkit@3.6.0?bundle';
```

A few flags from the [esm.sh documentation](https://github.com/esm-dev/esm.sh) are useful to know:

- `?bundle` bundles the module's dependencies into one file, which reduces the number of requests.
- `?standalone` goes further and inlines external dependencies too, except `peerDependencies`.
- `?deps=react@18.3.1` pins a shared dependency so you don't end up with duplicated sub-trees across imports.

The trade-off is deduplication, and it can go the other way too. esm.sh bundles each output on its own, so a shared dependency gets inlined into several of them. If that dependency keys a singleton on class identity, the duplicated copies are no longer the same class, and you get competing instances. That is actually why the page above serves `@studiometa/js-toolkit` with `?bundle=false`: with the default bundling, js-toolkit shipped two copies of its service classes, so a component writing to one `ScrollService` and a decorator reading from the other never agreed, and scroll-driven components stopped updating. Serving the un-bundled files gives every importer the same module, at the cost of the waterfall you saw above. So bundle for speed, but keep it off where correctness depends on a single shared instance, and preload the deep modules to pay down the waterfall.

### Preloading the deep modules

When you do need granular modules, the native lever is [`<link rel="modulepreload">`](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/rel/modulepreload). It tells the browser to fetch a module right away, in parallel, before it is discovered through the import chain. If you preload the deep dependencies, they load together instead of one level at a time. This is what Vite generates for you automatically, and buildless you write it by hand.

```html
<!-- Don't: import the entry and let the browser discover the rest one level at a time -->
<script type="module">
  import { Base } from 'https://esm.sh/@studiometa/js-toolkit@3.6.0';
</script>

<!-- Do: declare the deep modules up front so they load in parallel -->
<link rel="modulepreload" href="https://esm.sh/@studiometa/js-toolkit@3.6.0/es2022/Base/Base.nobundle.mjs" />
<link rel="modulepreload" href="https://esm.sh/@studiometa/js-toolkit@3.6.0/es2022/utils/dom/index.nobundle.mjs" />
<script type="module">
  import { Base } from 'https://esm.sh/@studiometa/js-toolkit@3.6.0';
</script>
```

`modulepreload` has shipped in every major browser since September 2023, and it is currently the only mechanism that lets you attach an `integrity` hash to the whole graph, as [Guy Bedford explains in detail](https://guybedford.com/es-module-preloading-integrity). The catch is maintenance: you have to keep the list of preloads in sync with the real dependency tree, which is the work a bundler was doing for you.

### Import maps solve versioning, not discovery

Import maps are the other piece everyone reaches for, and they are useful, but it helps to be clear about what they fix. They decouple the specifier from the versioned URL, which solves versioning and cache-invalidation cascades: when a deep dependency changes, you update one entry instead of rewriting every `import` and busting the cache down the chain.

```html
<!-- Don't: expect the import map alone to fix load performance -->
<script type="importmap">
  { "imports": { "@studiometa/js-toolkit": "https://esm.sh/@studiometa/js-toolkit@3.6.0" } }
</script>

<!-- Do: pair it with modulepreload so the graph is both mapped and preloaded -->
<script type="importmap">
  { "imports": { "@studiometa/js-toolkit": "https://esm.sh/@studiometa/js-toolkit@3.6.0" } }
</script>
<link rel="modulepreload" href="https://esm.sh/@studiometa/js-toolkit@3.6.0/es2022/Base/Base.nobundle.mjs" />
```

An [import map](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/script/type/importmap) doesn't flatten the waterfall. It rewrites specifiers, but the browser still discovers deep modules at the same time. Import maps help with maintainability, preloading or bundling help with speed.

### A top-level import only warms discovery

A trick I kept seeing is to put a bare `import 'package';` at the top of your entry, so that a later `import { foo } from 'package'` doesn't create a new request. This is partly a misconception: the second import never creates a request in the first place. ES modules are keyed by their resolved URL in the module map, so a module is fetched and evaluated once no matter how many times you import it.

What the top-level import actually does is move the discovery earlier: it pulls the module into an earlier request wave instead of leaving it to be found deep in the graph. I measured it on a local server with 120 ms of latency per module:

- discovered only through a deep chain: fetched at ~518 ms
- bare `import` at the top of the entry: fetched at ~170 ms
- `<link rel="modulepreload">`: fetched at ~15 ms

It is the same single request in the three cases, only the timing changes. `modulepreload` is the earliest because the HTML preload scanner sees it before the entry module runs, while the top-level import is only discovered one level in. The top-level import is useful when you control the entry but not the `<head>`, otherwise I would preload.

### Dynamic imports only defer the waterfall

Moving an `import` to a dynamic `await import()` lets the rest of your code run while the dependency loads, which feels like a fix. It doesn't remove the waterfall though, it only moves it later in the timeline. If that chain is on your critical path, deferring it only changes when the user waits.

## What I do in practice

I start with the esm.sh bundling flags, since they cost nothing and remove most of the depth, then add `modulepreload` for the modules that still need to stay granular. Import maps come on top for versioning, not for speed, and I keep dynamic imports for what is genuinely off the critical path.
